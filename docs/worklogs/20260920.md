## Compile overlay: the precompile ran on the UI thread

- User report: "compiling progress bar don't work for game".
- Root cause: `Emulator::CompleteLaunch` hops to the UI thread for `SetIcon` and the game config
  callbacks, then runs `LoadUserModule`, `FinishLoadingUserModule`, and `LaunchModule` on it.
  `FinishLoadingUserModule` runs the AOT precompile and joins the workers. The Android main looper
  sat inside a native looper callback for the whole compile. No Java post ran, sync or async. The
  overlay stayed at "Starting" and Android raised an ANR.
- Device evidence (Banjo-Kazooie, pid 29009, start 15:08:43): ANR at 15:09:41; after 8 minutes the
  main thread had 18 utime ticks and 241 voluntary switches, the Emulator thread 2 ticks, six
  PrecompileJIT workers about 9,000 ticks each, the AotCompileWatcher 26 ticks. `debuggerd -b`
  needs root, so the `/proc` thread table is the evidence.
- Fix: on Android `CompleteLaunch` runs on the emulator thread. Only the two `SetIcon` calls and
  the config callback loop hop to the UI thread. Other platforms keep the whole-function hop.
  `mAotSawMarker` is volatile. NDK clang syntax check passes.
- MCP server: commit `2e8c7975a0` left `lstrip('\')` in `tools/mcp/xenia_thor_mcp.py`, a syntax
  error. The server could not start this session. Fixed. `xenia_backtrace` now falls back to the
  `/proc` thread table when `debuggerd` refuses.
- New script: `tools/thor/aot_overlay_test.py`. It launches through the VIEW intent, records the
  watcher and watchdog lines, takes screenshots, and samples the largest free VA gap from
  `/proc/<pid>/maps` every 30 s.
- Second bug, not fixed here: the same run died at 15:19:56 with SIGABRT in PrecompileJIT,

## Object cache off on the play-button path; delete option; re:Blue levers; slab JIT memory

- User questions: where is compiled code written, how is memory used, and a delete option.
- Finding: the LLVM object cache wrote nothing since the toggle rework. The toggle puts
  `cpu_llvm_object_cache=true` in the launch bundle, and `ensureObjectCacheDefaults` returned
  early on that key without setting the path (`LLVMobjcache GATE ... path_set=0`). Every launch
  recompiled the title. The 6,608 files on the device were from 2026-09-18.
- Fix: `xenia_main.cc` defaults `cpu_llvm_object_cache_path` to `<files>/objcache` on Android
  ARM64; the Java early return now keys on the path and keeps the toggle's bool values.
- Device (APK `d5ac19715f293a2b`, Blue Dragon, script `tools/thor/aot_cache_cold_warm.py`):
  cold 19,884 functions in 414 s, 18,158 objects, 89 MB in `objcache_v3_opt2_bB23AE1BF`; the
  engine pruned the old build's directory (6,607 files). Warm: 19,884 functions in 15.7 s.
- Where the code lives: one .o per function under `files/objcache/objcache_v<N>_opt<O>_b<stamp>/`,
  about 5 KB each on disk. In memory, JITLink's InProcessMemoryManager mmaps one block per
  object and mprotects it: one 4 KB r-x page and one 4 KB r-- page per function, adjacent,
  never mergeable. Maps census: 2,841 + 2,841 VMAs at 2,841 functions, 14,181 + 14,181 at
  14,181 (+374 s), RSS 734 MB. `vm.max_map_count` 65,530 is reached near 32,000 functions.
  That is the Banjo, Gears, and MagnaCarta 2 abort. Raw maps under `scratch/mcp/maps/`.
- Delete option: Settings shows "Compiled code cache: N MB, N functions, N builds" with the
  location and a "Delete compiled code cache" button (confirm dialog, background delete).
  Built and installed; the button itself is not exercised yet.
- Slab JIT memory: `XeSlabMemoryMapper` (llvm_object_cache.cc) with `MapperJITLinkMemoryManager`,
  64 MB rwx slabs, no per-segment mprotect, so one VMA per slab. Built (NDK), not installed:
  the device was in use (foreground `com.armsx2`) when the install ran, so the install refused.
  Test owed: Blue Dragon warm run, then Banjo-Kazooie cold (37,632 functions) must survive.
