## Compile overlay: the precompile ran on the UI thread

- User report: "compiling progress bar don't work for game".
- Root cause: `Emulator::CompleteLaunch` hops to the UI thread for `SetIcon` and the game config
  callbacks, then runs `LoadUserModule`, `FinishLoadingUserModule`, and `LaunchModule` on it.
  `FinishLoadingUserModule` runs the AOT precompile and joins the workers. The Android main looper
  sat inside a native looper callback for the whole compile. No Java post ran, sync or async. The
  overlay stayed at "Starting" and Android raised an ANR.
- Device evidence (Blue Dragon, pid 29009, start 15:08:43): ANR at 15:09:41; after 8 minutes the
  main thread had 18 utime ticks and 241 voluntary switches, the Emulator thread 2 ticks, six
  PrecompileJIT workers about 9,000 ticks each, the AotCompileWatcher 26 ticks. `debuggerd -b`
  needs root, so the `/proc` thread table is the evidence.
- Fix: on Android `CompleteLaunch` runs on the emulator thread. Only the two `SetIcon` calls and
  the config callback loop hop to the UI thread. Other platforms keep the whole-function hop.
  `mAotSawMarker` is volatile. NDK clang syntax check passes.
- MCP server: commit `2e8c7975a0` left `lstrip('\')` in `tools/mcp/xenia_thor_mcp.py`, a syntax
  error. The server could not start this session. Fixed. `xenia_backtrace` now falls back to the
  `/proc` thread table when `debuggerd` refuses.
- New script: `tools/thor/aot_overlay_test.py`. It launches through the VIEW intent, records the
  watcher and watchdog lines, takes screenshots, and samples the largest free VA gap from
  `/proc/<pid>/maps` every 30 s.
