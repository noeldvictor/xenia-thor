## Compile overlay, MCP server, no-cvar rule

- User report: the "Compiling game code" overlay did not show, and the compile used little power.
  Log evidence from the 17:05 Banjo-Kazooie launch: the native precompile ran and logged progress
  (5,120 of ~33,414 functions at +80 s, about 64 functions per second); the app's UI watchdog logged
  the main thread wedged at +4 s (sync and async messages both stalled, Java stack idle in
  nativePollOnce); the process was force-stopped by another process at 17:07:41.
- Compile speed: the LLVM object-cache path holds one compile lock per function, so a cold compile is
  single-threaded by design. A new APK means a cold object cache. Not from today's ports.
- Fix landed: the overlay now polls a native `PrecompileStatus` (src/xenia/cpu/precompile_status.h)
  through `nativeGetAotProgress` instead of tailing logcat from inside the app. The main-thread wedge
  is still open; `xenia_backtrace` (debuggerd -b) is the tool to read its native stack.
- New: `tools/mcp/xenia_thor_mcp.py`, a stdio MCP server over adb, registered in `.mcp.json`,
  documented in CLAUDE.md section 9. 17 tools: status, preflight, launch, stop, logs, AOT progress,
  fps, screenshot, backtrace, threads, memory, config get and set, build, install, git head.
- User rule (CLAUDE.md directive 17): no more cvars. Ship behavior as app defaults; test only what the
  play button runs. `xenia_launch` sends the launcher's VIEW intent and passes no extras.
- Installed on the Thor at 17:2x: APK sha256 prefix `3926a36242993e39`. The overlay test launch was
  interrupted by the user before it ran. Not verified on device yet.
